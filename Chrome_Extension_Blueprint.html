▼ 🧩 Step 1: Manifest V3 Architecture & Sync Engine

Building modern Chrome Extensions requires strict compliance with Google's Manifest V3 specifications. Below are the foundational architectural decisions established during our build:

Key Insight: Manifest V3 completely removes persistent background pages in favor of event-driven, ephemeral Service Workers that automatically shut down after inactivity to preserve system RAM.

1.1 Core Manifest V3 Architectural Pillars

  • Service Worker Lifecycle: Background logic runs in background.js. Never rely on global window/DOM variables inside service workers. Store persistent state in chrome.storage.local.
  • Content Scripts vs Network Interceptors: Use content scripts for DOM inspection and floating overlays. Use webRequest/declarativeNetRequest interceptors to catch API payloads clean without DOM parsing latency.
  • 100% Test Case Enforcement: Only sync code when the target submission passes 100% test cases. Ignore partial or failing attempts to avoid polluting user repositories.
  • Conflict-Safe Commit Queue: Execute GitHub API commits sequentially with a lock queue. Parallel async pushes to the same branch cause Git 409 conflict errors.

1.2 Permission Minimization Strategy

Excessive host permissions (like <all_urls> or http://*/*) trigger mandatory manual Google Web Store security audits, extending review times from 2 hours to 2+ weeks.

Permission Purpose Review Risk
storage Save PAT tokens, user settings, and problem counts locally 🟢 Low Risk (Instant Auto-Approve)
declarativeNetRequest Intercept problem submission payloads in real-time 🟡 Medium Risk (Standard Review)
host_permissions Restricted strictly to target domain (e.g. *://takeuforward.org/*) 🟢 Low Risk (Targeted domain scope)

▼ 🎨 Step 2: Web Store Presentation Cards & Asset Pipeline

Chrome Web Store conversion rates heavily depend on crisp, presentation-grade graphics. Generic raw screenshots look unpolished and reduce install rates by up to 60%.

Design Rule: Web Store screenshots must be rendered at exactly 1280x800px inside a presentation card containing ambient radial glow halos, floating browser mockups, and macOS traffic light window headers.

2.1 Visual Asset Specifications

  • 1280x800 Presentation Cards: Built on a dark `#0b1120` canvas with multi-layered Fire Orange (`#f97316`) and Royal Blue (`#2563eb`) radial glow spheres.
  • macOS Dark Window Frames: Wrap screenshots in a dark `#1e1e26` header bar with vector Apple traffic light dots (🔴 `#ff5f56`, 🟡 `#ffbd2e`, 🟢 `#27c93f`).
  • Address Bar & Vector Status Dots: Draw clean address bars containing green status dots (`●`) and dynamic URL truncation (`...`) to eliminate text clipping.
  • Small Promo Tile (440x280px): Compact promotional card featuring high-contrast typography, extension logo, and `MANIFEST V3 READY` badge.
  • Marquee Promo Tile (1400x560px): Wide banner for store search features with Fire Orange glassmorphism background glow.

▼ 📄 Step 3: README & Documentation Engineering

A concise, well-structured GitHub README turns casual visitors into stars and active users. Follow these strict documentation invariants:

Em-Dash Ban Mandate: Do NOT use em-dashes (—) in documentation or README markdown. Replace all em-dashes with colons (:) or simple hyphens (-).

3.1 README Best Practices

  • High-Res Image Cache-Busting: Append ?v=5 query parameters to all image paths in `README.md` to force GitHub's Camo CDN proxy to invalidate stale cached images instantly.
  • 1-Row Horizontal Supported Languages Table: Instead of vertical bullet lists or empty top headers, format supported languages in a clean 1-row table header directly containing the items.
  • Collapsible Accordions: Wrap Developer Setup, Advanced OAuth, and FAQs inside <details><summary> dropdowns to keep the main flow concise.
  • Single License Badge: Avoid duplicating a bottom `## License` section if an interactive MIT License button already exists in the header badges.
  • Empowering Footer: Use professional, human-crafted wording like `Crafted with ❤️ for Problem Solvers by Mohit Arora`.

▼ 🐞 Step 4: Exhaustive Bug Log & Technical Fixes

Every complex build encounters unexpected runtime & rendering glitches. Here is our master resolution ledger:

Issue / Bug Observed Root Cause Production Resolution
Emoji Square Box Outline (🗖) PIL Pillow fallback font failed to render Unicode emoji symbols like ⚡ in image scripts. Replaced font emojis with vector filled circles (● green/orange) drawn directly onto the image canvas via ImageDraw.ellipse.
Address Bar Text Overflow Long URLs overflowed outside the browser header mockup bounds on store presentation cards. Created a custom dynamic string truncation helper appending trailing ... based on pixel width.
GitHub Table Blank Top Header Empty table headers (| | | | |) caused GitHub markdown to render an ugly blank line above table contents. Embedded data items directly into the first markdown | ... | header line.
Stale GitHub Image Cache GitHub's Camo CDN proxy served old cached versions of updated screenshots. Appended versioned cache-buster query parameters (?v=5) to all markdown image URLs.

▼ 🚀 Step 5: Web Store Submission & Review Audit

Follow this checklist before pushing your ZIP package to the Chrome Developer Dashboard:

  • Production Bundle Verification: Execute npm run build and verify all files in dist/ compile without warnings.
  • Clean Package Archiving: Zip contents of dist/ into TUFHub-v1.0.0.zip without including source code, node_modules, or scratch scripts.
  • Single Purpose Justification: Write a concise single-purpose justification in the developer dashboard explaining why your extension requires permission to access host domains.
  • Upload Visual Assets: Attach 1280x800 Store Presentation Cards, 440x280 Small Promo Tile, and 1400x560 Marquee Tile.

Success Criteria: When all steps above are checked, your extension will pass automated Chrome Web Store reviews in under 2 hours!
